# Health

<p className="lead">The Health tab tells you what will hurt your database soon, before it does: an ID about to run out, indexes nobody uses, a table vacuum can't keep up with, the queries taking the server's time. Each finding comes with its numbers and the SQL that fixes it, which you read and run yourself in a query tab.</p>

## Open the Health tab

Choose **View › Health**, or **Show health** in <kbd>⌘K</kbd> (it also answers to `vacuum`, `bloat`, `unused indexes` and `pg_stat_statements`). It opens as a tab called **Health** beside your query tabs. Each window has at most one, and it's saved with your other tabs.

Health works on Postgres and SQLite connections, and needs the window to be connected.

## When it reads

Health reads once when the tab first shows, and again when you press **Refresh**. It never reads on a timer, so a Health tab left open costs nothing. Switching to another connection or database starts it afresh.

On Postgres it reads only the catalog and the statistics views (`pg_catalog`, `pg_stat_*`), never a table's rows, so a read takes milliseconds even on a big database. It runs on a session of the window's own, never a query tab's. A check that waits more than a second on a table another session has locked (a migration's `ALTER TABLE`, say) gives up and says so under Not checked, and the rest still report. The Size tile waits the same way and is left out when it gives up.

## What the tab shows

At the top are tiles: **Size** (with tables and indexes apart), **Cache hits** (the share of reads served from memory), **Connections** (in use out of the server's limit, and how many are running a query now) and **Stats since** (when the server's usage statistics were last reset; Postgres 15 and later show it only after a reset).

Below them, **Needs attention** lists one card per check that found something, worst first. Each card has a word for how much it matters:

| Word | Means |
| --- | --- |
| Soon | Something breaks if it's left: inserts fail, writes stop, or the disk fills |
| Waste | It costs space and slows writes |
| Slow | It makes some reads or deletes slow |
| Upkeep | Routine maintenance hasn't kept up |
| Tidy | Something repeats something else |

Then come **Slowest queries**, **Fine** (the checks that found nothing) and **Not checked** (the checks your login isn't allowed to run).

## What it checks

| Check | Shows up when | Fix it offers |
| --- | --- | --- |
| IDs running out | An integer ID's sequence is past 70% of its range, with a date it runs out at the pace since the statistics were reset | `ALTER TABLE … TYPE bigint` (and `ALTER SEQUENCE … AS bigint` for a serial) |
| Transaction age | The database's oldest unfrozen transaction is past 50% of the limit, past which Postgres stops taking writes | `VACUUM (FREEZE, VERBOSE)` on the five oldest tables |
| Replication slots | An inactive slot holds more than 1 GB of WAL | `pg_drop_replication_slot` |
| Unused indexes | An index has had no scans since the statistics began, is over 10 MB, and isn't a primary key, unique or backing a constraint | `DROP INDEX CONCURRENTLY` |
| Repeated indexes | A btree index's columns lead another index on the same table, in the same order and with the same operator classes | `DROP INDEX CONCURRENTLY` |
| Foreign keys without an index | A foreign key's columns lead no valid btree index, on a table over 10,000 rows | `CREATE INDEX CONCURRENTLY` |
| Dead rows | Over 20% of the rows of a table over 10,000 rows are dead, and it hasn't been vacuumed in a week | `VACUUM (ANALYZE)` |
| Never analyzed | A table over 10,000 rows has never been analyzed | `ANALYZE` |
| Idle transactions | A session has sat idle inside a transaction for over 5 minutes | **Show in Sessions** |

On a partitioned table, index fixes leave out `CONCURRENTLY`, which Postgres doesn't allow there, and a foreign key is reported once, on the parent.

### On SQLite

SQLite keeps no usage statistics, so there are no unused-index, slow-query or session checks. Health checks **free pages** (more than 10% of the file and at least 1 MB, fixed by `VACUUM`), repeated indexes, foreign keys without an index, and tables over 10,000 rows with an index that have never been analyzed. Sizes come from walking the file's pages, which Rowkery does only for files up to 1 GB; for a bigger file the Size tile shows the whole file.

## Look at a finding

Click a card to open it in the inspector on the right. It says why the finding matters, lists each table or index with its numbers, says how far to trust it, and shows the SQL that fixes it, with a note where the fix has a cost (a table rewrite, a full-file `VACUUM`).

How far to trust it matters most for unused indexes: usage counts come from this server only, so an index used only on a read replica, or by a monthly job that hasn't run since the statistics were reset, looks unused here.

**Open in query tab** puts the fix in a new query tab. Health never runs a fix itself. You read it, run it with <kbd>⌘↵</kbd>, and the connection's [safe mode](/environments-and-safe-mode/) applies as for anything else you run. `CONCURRENTLY` and `VACUUM` can't run inside a transaction, so run them in a tab with no transaction open.

## Slowest queries

On Postgres, Health lists the ten queries that took the most of the server's time, from the `pg_stat_statements` extension: each query (its values show as `$1`, `$2`), its mean time, how many times it ran, and its share of the total. Click one to see it in full and open it in a query tab, ready for <kbd>⌘E</kbd> to [look at its plan](/query-plans/) once you fill in its values.

When `pg_stat_statements` is off, the section says so, and **How to turn it on** shows the steps: `CREATE EXTENSION pg_stat_statements;` in the database, which is enough on Amazon RDS and Google Cloud SQL, and on your own server adding it to `shared_preload_libraries` and restarting first.

## Your login's view

Postgres shows other logins' sessions and queries only to a superuser or a login with `pg_read_all_stats` (part of `pg_monitor`). Without it, idle transactions are listed under **Not checked** as needing pg_monitor, and slowest queries show only your login's own.

## The once-a-day check

You don't have to open Health to hear about the worst things. A few seconds after a window connects to a Postgres database, Rowkery reads its health once a day for that connection. If a **Soon** finding turns up (an ID running out, transaction age, a replication slot filling the disk), a toast names it, and its **Show health** button opens the tab. Nothing else gets a toast.

## Agents

Agents connected through MCP have a `health` tool with the same report, limited to the tables you shared: findings on other tables (and on tables made since the agent last read the schema, temporary tables and system catalogs) are left out, with a `left_out` count on the check, a foreign key whose parent you didn't share doesn't name it, and the slowest queries have every value replaced by `?`, with a query on a table you didn't share blanked, as in `sessions`. The tool shows the fix SQL but can't run it. See [MCP tools](/mcp-tools/).

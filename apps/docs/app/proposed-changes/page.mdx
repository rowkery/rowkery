# Proposed changes

<p className="lead">An agent never writes to your database. When it wants a change, it proposes the SQL with a reason, and the change waits in Rowkery until you try it in a dry run and commit it, or discard it.</p>

<Clip src="/clips/proposed-changes-review.mp4" poster="/clips/proposed-changes-review.webp" width={1180} height={700} alt="A toast says Claude Code proposed a change to orders and the Agents button shows 1. Review opens the proposed UPDATE with the agent's reason; Dry run shows two rows going from paid to refunded and rolls back; Commit saves them and a toast says Committed, 2 rows, orders." />

## How it works

1. The agent calls `propose_change` with INSERT, UPDATE or DELETE statements, a reason, and optionally how many rows it expects to change.
2. Rowkery checks the change (see [What gets refused](#what-gets-refused)) and queues it. Nothing runs. The agent gets an id back at once.
3. You review it, run a dry run, and commit or discard it.
4. The agent learns what you decided the next time it calls `check_proposal` with that id. Rowkery doesn't contact the agent; it finds out only when it asks.

## When a proposal arrives

<Shot src="/img/proposed-changes-arrival.webp" width={1100} height={100} alt="The foot of the window: the Agents button with an orange 1, and a toast reading Claude Code proposed a change to orders, with Review." />

- A toast names the agent and the table, such as "Claude Code proposed a change to orders", with **Review**. Several at once read "proposed 3 changes". The toast never replaces an Undo toast that is still showing, and <kbd>↵</kbd> doesn't trigger it.
- The Agents button at the foot of the schema column shows how many changes wait, in place of its green dot. While the count shows, the button opens the review; <kbd>⇧⌘A</kbd> still opens the Agents page.
- ⌘K **Review proposed changes** opens the review too, while anything waits.

In Claude Desktop and other clients that draw MCP Apps, the chat also shows the change as a card, with **Review in Rowkery** to open the review on it. See [Rows in the chat](/rows-in-the-chat/#a-proposed-change).

The review never opens by itself, so a proposal can't interrupt what you're typing. Rowkery checks for proposals every 3 seconds while a connection is shared or the Agents page is open, and only while the window is visible.

## The review

The review takes the place of the editor and grid. The list on the left shows every change waiting; the main column shows the one you picked; the column on the right shows who sent it and why.

<Shot src="/img/proposed-changes-review.webp" width={1100} height={620} alt="The review of a proposed change before the dry run: the list on the left with its one card, UPDATE orders with its SQL, the trigger orders_audit that runs on UPDATE, Dry run, and on the right Claude Code's reason with Discard, Open in a tab and a disabled Commit." />

| Part | What it shows |
| --- | --- |
| Head | The tables it changes, the connection, the database and how many statements |
| Each statement | Its verb and table, such as **UPDATE orders**, over its exact SQL |
| Triggers | Each trigger the statements would fire, such as "orders_audit runs on UPDATE orders", with "Triggers fire during the dry run" |
| Who and where | The agent's name, the connection and database, and how long ago it arrived |
| Reason | The agent's own words, up to 1,000 characters |
| Warning | "No WHERE: this deletes every row in orders" (or changes) for a DELETE or UPDATE with no WHERE |

Opening the review runs nothing: it only reads which triggers the tables have. **Commit** stays disabled until you run a dry run.

### The list

The list on the left shows every change waiting, oldest first, so you can review them in any order. Click a card, or press <kbd>↑</kbd> and <kbd>↓</kbd>, to open another one.

<Shot src="/img/proposed-changes-list.webp" width={1100} height={620} alt="The review with three changes waiting: a list on the left with UPDATE customers from Cursor, DELETE carts from Claude and UPDATE orders from Claude Code, each with its reason and age; the first is open beside it." />

Each card shows the verbs and tables, the agent's reason, which agent sent it and when. A card says "No WHERE" in red when a statement has no WHERE, or "3 rows · dry run" once you've run one. When the changes come from more than one connection or database, the card names it too.

## The dry run

Click **Dry run**. Rowkery runs the statements in a transaction and rolls it back, so nothing is saved.

<Shot src="/img/proposed-changes-dry-run.webp" width={1100} height={620} alt="After the dry run: the two rows the UPDATE changes, status paid struck through over refunded; 2 rows rolled back; the card in the list says 2 rows, dry run; on the right, 2 rows would change, Agent expected 2, and the changed column status." />

- Under each statement, the rows it changed: for an UPDATE, the old value struck through above the new one in each changed cell; new rows for an INSERT; the rows a DELETE would remove. Up to 200 rows show per statement, with "First 200 of 1,240 rows" beyond that.
- A statement that matches nothing says "No rows match, so this statement changes nothing."
- Beside Dry run, the total and "rolled back", such as "2 rows · rolled back", or "67 rows in 5 tables · rolled back" when the change reaches other tables.
- On the right, "2 rows would change" beside "Agent expected 2" when the agent gave a number, and the columns whose values change.

### Everything a change touches

Deleting one customer can delete their orders, their payments and every order item through foreign keys with `ON DELETE CASCADE`, and a trigger can write an audit row. The dry run counts all of it.

- The statement's head adds what other tables change, such as "1 row + 66 in other tables". The rows shown under it are the statement's own.
- On the right, the total counts every table, and each table gets a line with its count: "14 deleted", "1 added", "2 changed".
- A table the agent wasn't given, reached through a cascade or a trigger, says "not shared", and a warning names it. The change is still allowed: you see the counts before you commit. The agent hears nothing about that table.
- On Postgres, triggers that wait for COMMIT (deferred constraint triggers) fire at the end of the dry run, so their rows count too. A partition's rows count under its table.
- On SQLite, rows in a `WITHOUT ROWID` table show as "N more rows in tables Rowkery can't name".

Triggers run as the database defines them, so a trigger may read or write a table the agent wasn't given; that's the database's own logic, never the agent's SQL, and its writes show in the counts. It shows counts, not the rows themselves. Tables on another server (Postgres foreign tables) aren't counted, and anything a trigger does outside the database already happens during the dry run. A Postgres server with `track_counts` off keeps no counts, so only the statement's own rows show.

If another session holds the rows, the dry run waits 2 seconds, then stops: "Another session is holding these rows, so the dry run stopped after 2 s. Nothing was changed." Click **Dry run again** to retry. Each change keeps its dry run while you look at another one, so you can come back and commit without running it again.

## Commit

Click **Commit** <kbd>⇧⌘↵</kbd>. A single DELETE or UPDATE with no WHERE labels the button **Delete all rows** or **Update all rows**.

Before anything runs, Rowkery checks the change again from the start: the connection must still be shared, its tables still shared, and the SQL must still pass every rule. Then it runs all the statements in one transaction and commits only if each statement changes the same number of rows the dry run showed, in its own table and in every other table it reaches. An update or delete on a table with a primary key must also change the same rows: if the dry run removed order 17 and the commit would remove order 42 instead, nothing is saved, even though both remove one row.

| What happens | What you see |
| --- | --- |
| It commits | "Committed", with the rows and table (and "+ 66 in other tables" when it reached them), and the proposal leaves the queue |
| The rows changed since the dry run, in any table | Nothing is saved. "Nothing was saved: the rows changed since the dry run. Check the new one." A fresh dry run takes its place, ready to commit |
| An error before COMMIT | "Couldn't commit" with the server's message. Nothing was saved, so you can try again |
| The connection dropped during COMMIT | Rowkery can't know whether it was saved, so it never retries. The agent is told it failed, and you should reload the table to check |

During a commit, each lock wait gives up after 3 seconds and each statement after 15.

## Discard

Click **Discard**, type a note for the agent if you want (up to 500 characters), and press <kbd>↵</kbd> or click **Discard** again. A toast says "Discarded". <kbd>Esc</kbd> backs out of the note without discarding.

**Open in a tab** discards the change and puts its SQL in a new query tab on that connection, where you can edit it and run it yourself. The agent is told you opened it to change it, so its version won't run.

## What the agent learns

`check_proposal` answers with one of these states:

| State | When |
| --- | --- |
| `waiting` | Nobody has decided yet |
| `committed` | You committed it, with the rows each statement changed |
| `rejected` | You discarded it, with your note if you wrote one, and a hint not to send it again |
| `failed` | The connection dropped during COMMIT |
| `expired` | Nobody decided within 24 hours |

A failed commit you can retry stays waiting; the agent hears `failed` only when the outcome is final.

## What gets refused

`propose_change` refuses, before anything is queued:

- a connection whose safe mode is **Read-only**: it takes no changes, proposed or not;
- anything other than INSERT, UPDATE and DELETE: no schema changes, no function calls on their own, and no CTEs (`WITH …`);
- `RETURNING`, `UPDATE … FROM` and `DELETE … USING` (the agent is told to name the rows with `WHERE … IN (SELECT …)` instead);
- tables that aren't shared, including through a view or subquery;
- any mention of a masked column, whether reading, writing or filtering on it (see [Sensitive columns and Presenting](/sensitive-columns-and-presenting/));
- on Postgres, functions defined in the database, and the built-in ones agents can't call in a query;
- more than 20 statements, SQL over 20 KB, a missing reason, or a reason over 1,000 characters;
- a sixth waiting proposal on the same connection: five can wait at once.

The same checks run again before the dry run and before the commit, because the queue file could have been changed by something other than Rowkery.

## The queue

- Proposals are kept in `proposals.jsonl` beside your config, and decisions in `proposal-outcomes.jsonl`. They survive a restart: proposals still waiting show in the Agents button's count when you reopen Rowkery, without a toast for each.
- A proposal nobody decides on expires 24 hours after it arrived, and leaves the queue.
- The review closes on its own once nothing is left to review. **×** or <kbd>Esc</kbd> closes it earlier; the proposals keep waiting.
- If you stop sharing a connection, its proposals can't run: "This connection is no longer shared with agents, so the change can't run. Discard it, or share the connection again."
